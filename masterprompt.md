## 3.5 Background Processing

A background task does not automatically require a microservice.

Use internal job abstractions for:

- Corpus ingestion.
- Search indexing.
- AI execution.
- Email notifications.
- Scheduled tasks.
- File processing.
- Reports.
- Data reconciliation.

If a separate process is technically necessary, it must:

- Use the same codebase and release artifact.
- Have a clearly defined process mode.
- Share the existing identity and authorization authority.
- Use the canonical database ownership boundary.
- Avoid creating a second API or independent product.
- Be deployed only when justified.

Do not promise exactly-once arbitrary side effects.

Use idempotency, retry limits, checkpoints, and explicit failure handling.

## 3.6 Technology Selection

Do not select technologies from preference alone.

Audit existing choices and compare:

- Node.js / TypeScript.
- Fastify or another existing HTTP framework.
- React / Next.js.
- Existing UI packages.
- Existing ORM.
- PostgreSQL.
- Existing search capabilities.
- Existing workflow and job libraries.
- Existing telemetry.

Prefer the technology that minimizes total complexity and reuse cost.

Do not introduce Rust, Go, Python, Redis, a graph database, a vector database, or another service simply because it exists in a historical repository.

Introduce polyglot or additional infrastructure only when a measurable requirement justifies it.

## 4.3 Canonical Ownership Matrix

Matriks berikut menentukan batas utama. Rinciannya harus divalidasi saat audit dan menjadi sumber resmi dalam Domain Ownership Registry.

| Domain | Canonical ownership | Tidak boleh dimiliki |
|---|---|---|
| Identity | Accounts, principals, credentials, sessions | Historical person identity |
| Organization | Tenants, organizations, memberships, groups | Person biographies |
| Person | Real/historical persons, sourced identity and roles | Fictional character |
| Character | Fictional characters, canon, universe and arcs | System user and AI execution |
| Source Registry | Source artifacts, source versions and provenance | Full corpus content ownership |
| Corpus / RGBL | Works, expressions, editions, passages, exact text, translation and lexical records | Research verdict |
| Ontology / UNILEX | Canonical terms, concepts, definitions, aliases and semantic mappings | Every domain's descriptive text |
| Witness | Testimony, observations, witness statements and transmission records | Duplicate person identity |
| Event / LEGEND | Event records, chronology, places and event assertions | Narrative story ownership |
| Story / MFTL | Narrative, myth, folklore, motifs, story versions and story claims | Historical event canonical records |
| Evidence | Evidence records, support, contradiction and chain references | Original source artifact ownership |
| Research | Cases, hypotheses, research questions, methods and findings | Canonical scripture text |
| Legal / AWS | Legal sources, jurisdiction, legal applicability and arguments | General ethics engine |
| Relationship / CORRELATION | Reviewed cross-domain relationship edges | Duplicated domain entities |
| Assessment / Mizan | Assessment methodologies, versions, dimensions and results | Universal truth authority |
| Journey | Goals, missions, personal/community/global progress | System workflow state machine |
| Creative | Original creative works, drafts, production and derivative metadata | Source content canonical ownership |
| Media | Media manifests, metadata, object references | Physical storage implementation |
| AI Platform | Models, prompts, tools, agents, configurations and execution runs | User identity and domain canonical truth |
| Workflow | Process definitions, states, transitions and executions | Domain-specific canonical data |
| Publication | Editorial workflow and publication records | Original authoring data of every domain |
| Search | Derived indexes, search sessions and retrieval configuration | Canonical content |
| Platform Operations | Audit, logs, monitoring, jobs, notifications and configuration | Domain knowledge |

### Specific boundary rules

**Identity vs Person**

A system user is not automatically a canonical Person record.

Link them only through an explicitly authorized relationship.

**Person vs Character**

A real or historical person is not a fictional character.

A fictional representation must preserve its fictional classification and source.

**Character vs AI Persona vs Agent**

These are separate objects:

- Character: narrative identity.
- AI Persona: conversational identity.
- Agent: executable capability.
- User: security principal.

**Witness vs Person**

A witness is a role in a specific context.

The Witness domain owns testimony and attribution; Person owns the person identity.

**Story vs Event**

An event is not automatically a story.

One event may be represented by multiple stories, interpretations and reports.

**Source vs Corpus**

Source Registry owns the source artifact and provenance.

Corpus owns the textual work, expression, edition, passage and exact textual representation.

**Research vs Evidence**

Research formulates and evaluates questions and hypotheses.

Evidence stores the supporting and countervailing records used by research.

**Mizan vs Research**

Mizan owns evaluation methodologies and assessment outputs.

Research owns the cases and investigations that may consume them.

**Relationship vs Domain Relations**

Intra-domain relations remain inside the owning domain.

Cross-domain published relationships are managed through a reviewed Relationship/Correlation contract.

**Knowledge vs Domain Data**

Knowledge Explorer is an integrated discovery experience and read projection, not a second database owner for Corpus, Person, Story, Event or Research.

**Search vs Canonical Records**

Search indexes are derived and rebuildable. Search results never replace the authoritative data source.
