# Security and Privacy Blueprint

**Status: PROPOSED controls.** Threat model and policy details require review before production use.

## Trust boundaries

Browser is untrusted. API is the authentication/request boundary, not the domain authority. Addon services and QlOrm enforce domain validation, ACL and owner scope. External AI/storage/messaging providers receive only approved data under explicit contracts. Imported corpus and retrieved text are untrusted input.

## Required controls

- Deny by default; explicit model/action ACL and owner field; tenant scope only if adopted.
- Enforce authorization in server-side addon/service on every operation, including internal service calls and background jobs.
- Test cross-user/tenant reads and writes, private-field omission, role escalation and direct object references.
- Keep credentials and provider keys private; encrypt provider secrets at rest; write-only input and masked output; rotate/revoke path.
- Hash passwords with established password KDF; store only session-token hashes; expire/revoke sessions; secure cookie settings.
- Validate request size/type and domain constraints; prevent unsafe query construction; rate limit authentication and expensive AI/search paths.
- CSRF/origin protection for cookie-authenticated mutations; secure headers, TLS termination and cookie policy.
- Redact passwords, tokens, keys and unnecessary private testimony from logs, traces, errors and analytics.
- Separate operator/admin/reviewer/publisher permissions; audit sensitive administrative and publication actions.
- Rights check before import, display, transformation, indexing, export and publication.
- Data minimization, retention/deletion, export and incident response rules documented before launch.
- AI prompt injection isolation, tool allowlists, bounded runtime/cost, human review for canonical writes, no final religious/historical authority.

## Local evidence

Partner/provider/conversation models include owner fields. Provider secret is private and API-side code uses AES-256-GCM; password hash uses scrypt; session token is random and SHA256-hashed; cookie uses HttpOnly/SameSite=Strict and Secure in production. This is implementation observed in local workspace, not a complete security certification. API/database domain boundary and addon service ACL tests need work.

Inspected routes have no per-route default-deny policy, and ResearchRun get/list/cancel repository queries are not owner-scoped. The idempotency scope falls back to the request's `x-principal-id` header if a verified principal is absent. Reverse-proxy controls and actual deployment exposure were not inspected, so exposure is unknown; this is a source-level conditional fail-open risk, not a claim about a live deployment. Any future API must fail closed when auth is required and enforce owner scope in domain services/storage.

`ArsyBelovedLabs/rocksoul-browser-worker` `7645f5a41c3aa2d9466c69f5e9f95699992d733f` is a standalone Playwright automation API with no authentication, authorization or owner isolation in the inspected routes. Its create/list/get/cancel and approval endpoints are open; any caller can approve an action the worker paused for review. Each caller chooses its own allowed domains, private/local addresses are not prohibited, and the Playwright driver checks the page's final URL only after navigation/action, without intercepting every outgoing request. Treat the allowlist and approval pause as workflow behavior, not security controls. Full job JSON—including typed values, extracted output, errors and evidence paths—is persisted and returned without a retention/delete route; there is no queue capacity bound. Do not deploy or integrate this service. A future approved automation capability needs authenticated owner-scoped requests, role-bound approval, server-controlled egress checked before network access, minimal/redacted outputs, and bounded retention/queue controls.

Additional runtime limits from the same source: `readJson()` buffers `request.text()` before checking the byte cap, so the cap does not bound memory consumed while receiving a large chunked body. Playwright operations do not wire the supplied abort signal into in-flight browser commands, so cancellation/timeout may wait for a command timeout. The provided Docker image selects the mock driver and does not install Chromium; actual browser deployment is not demonstrated.

`ArsyBelovedLabs/rocksoul-code` `16a23af8548d23850d94c554ca2794929b17211b` is a separate OpenCode-derived developer tool, not a MoonWitness app/runtime. No live deployment was checked. Keep it out of MoonWitness runtime and data ownership.

`ArsyBelovedLabs/rocksoul-code-web` `f6d8e0f6c61587d81828d86b8b9206d311589e0c` is a high-risk autonomous coding control center. In the inspected `/api/opencode/[...path]` route, all GET/POST/PATCH/PUT/DELETE requests are proxied to OpenCode with server-side Basic credentials injected, without checking the caller's identity or owner. Its `/api/platform/[service]/[...path]` proxy also has no user/owner check and forwards orchestrator requests using `ROCKSOUL_INTERNAL_AUTH_TOKEN`. Therefore, any client that can reach these routes can exercise the server's OpenCode access and submit orchestrator requests; storing the password/token server-side does not protect these routes from their callers. The package's dev script explicitly binds `0.0.0.0`, while `start-local.ps1` sets `HOST=127.0.0.1` and does not override the CLI bind address. Compose maps published ports to host loopback, which narrows host access in that deployment configuration, but the inspected routes still have no application-user boundary. The launcher fallback and provided Docker env example target the sibling `moonwitness-api` workspace, not the selected `moonwitness-reborn`. The Compose file defaults the browser driver to mock and real runner execution to false; deployment behavior is unknown. Architecture claims of workspace isolation, human approvals, and audit evidence were not verified across the sibling services. Do not run this control center against the selected product workspace or adopt it as a service. If agent workflows are later approved, require authenticated identity, owner-scoped operations, server-enforced workspace bounds, authorization-bound approvals, egress restrictions, and bounded/redacted evidence before exposing them.

`ArsyBelovedLabs/rocksoul-gateway` `7a8bdc4cebc70132d015392a2b64118b581fc35f` has several useful controls: HMAC-SHA256 verification over raw webhook bodies, channel-qualified identity allowlisting, timing-safe comparison for its shared admin bearer token, optional HMAC signing to the orchestrator, and an empty allowlist rejects all identities. The request-size guard is incomplete for chunked bodies because `request.arrayBuffer()` buffers the body before measuring its actual size; JSON parsing also happens before signature verification. The timestamp is only syntax-checked, with no freshness window, while `X-Idempotency-Key` is caller-controlled and outside the body signature, so a captured valid body can be replayed with a different key. Its idempotency map grows without bound; arbitrary schedule payloads have no deletion/retention path; and a schedule's due time advances before routing, so a crash/failure can drop that run. The JSON file is single-process state and only audit events are capped at 10,000. Config binds `0.0.0.0`, and the example secrets are accepted if copied unchanged. Keep it outside product runtime; any approved channel ingress needs body streaming limits, replay protection, bounded retention, durable state and source-verified identity under the local owner/ACL model.

`ArsyBelovedLabs/rocksoul-orchestrator` `f5475234f6fa012a4214c6cccab1b7cbca2e781f` is a high-risk autonomous execution service. `ROCKSOUL_INTERNAL_AUTH_TOKEN` is optional and absent from its `.env.example`; without it, the HTTP handler skips authentication for every non-health route while the server listens on `0.0.0.0`. When set, the token is one shared bearer credential with no user/owner scope; `X-Actor-Id` and approval `resolvedBy` are caller-supplied. The `/ws` and `/v1/events/stream` paths upgrade in `main.ts` before the HTTP auth handler and broadcast recent/future global events even when the token is configured. API callers can resolve approvals and mark verification gates passed/waived; the gate endpoint checks only referenced artifact existence, not the underlying test result. The RBAC module's validation endpoint is not a route/tool execution guard in the inspected paths. `deploy-and-verify` performs a server-side fetch to a caller-controlled `targetUrl` and gives the same host to the browser worker without private-address filtering, enabling SSRF. Other exposed operations can execute OpenCode in configured workspaces and, when credentials exist, push branches/create draft PRs. Configured project roots restrict paths globally but do not isolate owners. JSON state/audit retention is unbounded. Do not expose this service or run it against `moonwitness-reborn`; any future agent feature needs mandatory authenticated identity, owner-scoped authorization, protected WebSockets, independently authorized approvals, execution-derived verification evidence, strict workspace/egress controls, sandboxing, and bounded/redacted retention.

`ArsyBelovedLabs/rocksoul-runner` `232aa7a217ebd6bad01273a682635360c12e5946` defaults to dry-run and has direct argv spawning, obvious dangerous-command denials, canonical workspace/cwd checks, plan expiry, and execution budgets. It is also explicitly not an authentication service: every route is unauthenticated, callers can register any existing absolute path accessible to the service, self-approve by submitting an `approvedBy` string, execute plans, and read plan/output by ID; recent plan IDs are exposed in the global audit feed. If `ROCKSOUL_REAL_EXECUTION=true`, approved commands run as the service user with the full inherited `Bun.env`; the cwd is confined, but command arguments can still address any file the process can access. The risk classifier trusts the basename of the submitted executable, allowing a custom binary named `ls`, `echo`, or another low-risk utility to bypass the approval requirement. The approval gate cannot protect against an unauthenticated caller. Request bytes are buffered before the configured size is checked, and plan/workspace maps have no cap or expiry cleanup; output and concurrency budgets only limit command execution. Keep it out of product runtime and do not expose it. Any future command execution needs user/owner authentication, an administrator-controlled workspace root, verified executable policy, OS/container filesystem and process isolation, server-authorized approvals, minimized environment, streamed request limits and bounded/redacted result retention.

`bjo163/rocksoul-mind` `6fc918beb68a0d8c40452338df6319fe168014ba` is a public Apache-2.0 MiniMind code fork. The inspected `scripts/serve_openai_api.py` defines an unauthenticated `/v1/chat/completions` route and binds Uvicorn to `0.0.0.0:8998`; its request schema does not set explicit caps for message/tool counts or `max_tokens`. A reachable instance could consume model resources and return generated content to any caller. Treat it as a local research demo, not a production service; any approved inference boundary needs `moonclient` contracts, authenticated identity, request/generation quotas, bounded inputs, owner-scoped access and operational monitoring. The code license does not establish rights for separately released/downloaded model checkpoints or training data; record artifact-level source, license, hash and evaluation before considering use.
