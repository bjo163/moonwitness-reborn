# Repository Capability Matrix (D02)

**Status: SUBSTANTIAL / CENSUSED AND MAPPED.** This is the canonical D02 matrix. Every repository admitted to the candidate census now has its own row; group rows have been removed. The matrix records repository-level facts at the listed branch/SHA and explicitly leaves unknown data unknown. Every row — repositories and XV component slices alike — additionally carries a target canonical owner in the [estate-wide roll-up](#estate-wide-capability--canonical-owner-roll-up), so no mapped capability is left without a stated landing place or an explicit reason for having none.

**Candidate census method (2026-11-01, corrected).** The census is executable, not descriptive: [`docs/audit/tools/repository_census_gate.py`](tools/repository_census_gate.py) re-queries GitHub and diffs itself against this table, exiting non-zero on any gap — a missing or duplicate row, a census SHA that no longer appears in the table, a broken cell count, an unpinned marker, or an estate-wide roll-up that fails to assign each matrix row exactly one target owner (`PYTHONIOENCODING=utf-8 python docs/audit/tools/repository_census_gate.py`, authenticated `gh` required; deliberately not wired into CI — the estate scan is a planning tool). The census enumerates repositories from **three sources and takes their union**, because no single endpoint is complete: GraphQL `search(query:"user:<owner>")` with cursor pagination, REST `users/<owner>/repos?type=all` with `--paginate`, and REST `orgs/<owner>/repos?type=all`. The union is then filtered by a name-or-description regular expression over `moon|mw|xv|xiv|rocksoul|witness|allah|crayon|empire|orbit|mesh|ontolog|divine|antikythera|propet|rgbl|arsy|a-l-l-a-h|hbd|denpa|echolog|lumen|sentinel|mizan`, and any repository whose SHA cannot be read from the listing is resolved individually through `repos/<name>/git/ref/heads/<default_branch>`.
**Why the union is mandatory.** An earlier single-source census built only from `user:` search was wrong in two ways, and both were found by re-running the check rather than by reading the same page twice. First, GitHub repository search omits forks unless `fork:true` is requested: `search(q:"user:bjo163")` reports `total_count` 200 while `search(q:"user:bjo163 fork:true")` reports 260, so 60 of the account's repositories are forks that plain search cannot return at all. The union census recovered 259 distinct `bjo163` names (search 200 + REST `users/` listing 131, 72 overlapping), i.e. 59 fork names beyond what the old method could see — including `bjo163/rocksoul-mind` and, far more consequentially, `bjo163/surealdb-rebrand-mwdb`, a 52 MB SurrealDB fork carrying its own local-first journal, sync and Merkle-proof crates. Second, `ArsyBelovedLabs` is an organization, so `users/ArsyBelovedLabs/repos` returns 2 repositories while `orgs/ArsyBelovedLabs/repos` returns the real 27. Any future census must keep all three sources or it will silently understate the estate.
**Result.** **90 filter-matched candidates** — 84 with an exact default-branch SHA and 6 with no commits at all (`crayon`, `dev-mw-design`, `mw-blueprint`, `orbit`, `propeth`, `rocksoul-igate`). Two more rows are carried deliberately even though the filter cannot see them: `zenix-id/orbit` (different owner, pinned at `cf5258c4e62a5858a253a586d1cfb4cf9fdd78ff`) and `bjo163/ecosystem-foundation` (no filter keyword, but it asserts superseded foundation authority). That is **92 tracked rows**, each verified present exactly once. The matrix previously reported 87, then 88, candidates from the incomplete single-source method; earlier counts in this audit (91 broad, 75 keyword, 19+13 code-search, "310 accessible repositories") were un-normalized screens over different terms and sources, and all are superseded by this union census.
**The estate is a moving target.** `bjo163/mooncripsy` was created at 2026-11-01T07:11:52Z, appeared on the second census pass as an empty repository, received its first commit at 2026-11-01T07:23:29Z while this matrix was being written — so its row was rewritten from "no content to audit" to a full content assessment within one hour — and has since advanced twice more, at 07:45:06Z and at 08:09:06Z, both after this document had been finalised, each time caught by the coverage check on re-run. It is deliberately kept under the literal-SHA assertion so that continued activity in it keeps surfacing as a gate failure rather than as a stale row. That later commit matters more than a timestamp: it adds `PRODUCT.md` and `.impeccable/build/.gitignore` and edits the desktop renderer and its smoke test, i.e. an automated product/design agent is writing into this third-party copy inside this account, so the row is a point-in-time assessment of a moving codebase rather than a settled one. `bjo163/moonwitness-reborn` showed **twelve distinct default-branch tips** across the same morning (`3acab11…` 04:09:44Z through `7d801c3…` authored 07:54:20Z, re-read 08:29Z), moving twice more while its own row was being re-pinned (`5fbf137…` → `a585b94…` → `cc28930…`) and twice more again after the matrix was thought finalised — and the repair landed: at `7d801c3…` the `validate` check-run that this matrix records as failing at three earlier tips concludes **success**, which removes the CI caveat from this row without removing the moving-target constraint: a few minutes later those same commits were **merged and released**: PR #1 ("Bind MoonClient fetch to the global receiver") and PR #2 ("Rilis v0.1.0") both landed on `main`, tag `v0.1.0` and release "MoonWitness v0.1.0" now exist, and `main` carries classic branch protection with a required `validate` status check (`strict`, `enforce_admins` enabled) while the rulesets endpoint still returns an empty list. This workspace's HEAD is on branch `dev`: `7e7a66c…` was the pushed `origin/dev` tip when this row was pinned — two commits **ahead** of `origin/main` and green there (`validate` success, Actions run `41291851818`) — and this audit's own baseline, `8016edc…` plus its child `85feec0…` (R-49/R-53), sits on top of it, so the branch moved again while this document was being read; being ahead of `main` is not the same claim as being unpushed, and an earlier sentence in this paragraph read it that way. Which side of which branch a reader is on changes every few minutes, so the numbers are read from `requirements_traceability_gate.py` (`BASELINE_TRACKING` prints branch, upstream, unpushed count, tracked-modified count, HEAD, `origin/main`, ahead and behind) and never kept in this sentence. The SHA-literal coverage check earned its place immediately: on re-run it flagged `bjo163/moonwitness-reborn` and then `bjo163/mooncripsy` as stale before this paragraph was written, which is exactly the failure mode a name-only diff would miss. Because the reborn branch is under continuous concurrent commits from another session, the SHA-literal assertion cannot ever stay satisfied for it — so it is the one explicit exemption, and its row carries an observed-at timestamp and commit subject instead; every other repository, including the two that moved, must satisfy the literal check. The census must still be re-run against the matrix before any planning phase is treated as current: the check re-queries all three sources, diffs returned names against the table rows, and requires each census SHA to appear literally in the table, so a new, renamed, forked or advanced repository surfaces as a missing or stale row instead of passing unnoticed.

This matrix does **not** certify a complete source-file, branch, issue, release, license, contributor or data audit. Rows marked "root tree and README inspected" are evidence-grade only for the items listed in their Evidence column; rows marked "metadata only" verified SHA, visibility and license and nothing else.
