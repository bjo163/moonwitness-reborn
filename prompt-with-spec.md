# PHASE 9 — OBJECTIVE ACTION SCORING SYSTEM (MANDATORY 1–100)

**EVERY ACTION MUST HAVE A SCORE BETWEEN 1 AND 100.**

Tidak boleh ada action yang tidak memiliki score.

## 9.1 Seven Scoring Dimensions

Setiap dimensi dinilai dari 0–10.

| Dimension | Weight | Definition |
|---|---:|---|
| Impact & Value | 25% | Besarnya value atau dampak |
| Urgency | 15% | Seberapa mendesak |
| Strategic Alignment | 15% | Kesesuaian dengan project vision |
| Evidence Confidence | 15% | Kekuatan evidence |
| Risk Reduction | 10% | Pengurangan risiko |
| Reusability & Leverage | 10% | Dampak lintas module, pengguna, atau workflow |
| Feasibility | 10% | Kelayakan berdasarkan effort dan dependency |

## 9.2 Mandatory Formula

```text
Action Score = ROUND(
    Impact × 25 / 10 +
    Urgency × 15 / 10 +
    Strategic Alignment × 15 / 10 +
    Evidence Confidence × 15 / 10 +
    Risk Reduction × 10 / 10 +
    Reusability & Leverage × 10 / 10 +
    Feasibility × 10 / 10
)
```

Maximum = 100.

Setiap rating harus mempunyai justification.

## 9.3 Score Classification

| Score | Classification |
|---:|---|
| 90–100 | Exceptional |
| 75–89 | High Value |
| 60–74 | Valuable |
| 40–59 | Moderate |
| 20–39 | Low |
| 1–19 | Minimal |

## 9.4 Score vs Priority

Jangan menyamakan Action Score dengan Priority.

Priority:

- CRITICAL.
- HIGH.
- MEDIUM.
- LOW.

Priority ditentukan oleh severity, operational urgency, security risk, data risk, user impact, dan blocking dependencies.

## 9.5 Score Validation

Setiap action harus mempunyai:

- Seven-dimension breakdown.
- Weighted contribution.
- Final calculated score.
- Score rationale.
- Evidence confidence.
- Priority rationale.

Jangan memberikan score tinggi tanpa evidence.

Jangan memberi score tinggi hanya karena teknologi baru atau populer.

Jika action hanya merupakan investigation, score pekerjaan investigation, bukan masalah yang belum terbukti.

Jangan memanipulasi score.

**PHASE 9 OUTPUT:** Objective Action Score Registry.

## 10.2 Directory Responsibilities

**`spec/README.md`**

Explain:
- Purpose of the specification system.
- Navigation.
- Folder conventions.
- Action ID rules.
- Status definitions.
- Specification versioning.
- Audit batch references.
- How engineers and coding agents should consume specifications.

**`spec/audits/<AUDIT-ID>/`**

Stores the complete audit snapshot and overall research, analysis, action registry, scoring, roadmap, and evidence indexes.

**`spec/actions/<ACTION-ID>-<slug>/SPEC.md`**

Stores the full specification of exactly one action.

**`evidence.md`**

Optional supporting evidence file if the evidence is too extensive for `SPEC.md`.

**`artifacts/`**

Optional supporting materials such as:
- Architecture diagrams.
- Data-flow diagrams.
- UI/UX references.
- Component maps.
- API examples.
- Schema comparisons.
- Test matrices.

Do not generate unnecessary supporting files.

## 10.3 One Action — One Specification Rule

Setiap Action ID harus memiliki folder yang unik.

Contoh:

```text
spec/actions/ACT-0001-centralize-api-error-handling/SPEC.md
spec/actions/ACT-0002-fix-user-session-expiry/SPEC.md
spec/actions/ACT-0003-standardize-shared-ui-components/SPEC.md
spec/actions/ACT-0004-improve-mobile-navigation/SPEC.md
```

Rules:

- One Action ID = one action folder.
- One action folder = one mandatory `SPEC.md`.
- All actions must link to their specification from the Master Action Registry.
- Action ID must remain stable across audit and roadmap documents.
- Do not duplicate specifications under multiple directories.
- Cross-reference related actions rather than repeating their specifications.
- If an existing action is refined, maintain specification revision history.
- Do not silently replace existing authoritative specifications.
- Inspect the existing `spec/` directory before creating anything.
- Preserve useful existing specification content.
- Resolve filename collisions without destructive overwrites.
